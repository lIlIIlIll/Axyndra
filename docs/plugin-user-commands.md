# Installed user Commands and continuation

An installed Command may return `axyndra.command-proposal/v1` with exactly `schema`, `local_tool`, `input` and an optional `user_control`. The host freezes the complete response. Only the same installed package's declared Tool can be selected. Parsing the Command grants no Tool permission. The real Application user invocation, mounted generation, package digest, original argument digest and thread remain bound until completion.

The Application sends the original ToolCall through its existing canonical Direct gateway. A document preparation read and the document mutation retain separate actual approvals in the same Run. `ApplicationSession.approval()` and `decide()` expose those approvals to the existing TUI, JSONL RPC and CLI. An invalid decision preserves the current review. Approving a stage never reruns the Command parser. Reject, cancel and EOF settle the actual prepared work; generation changes cannot redirect a retained proposal. The CLI `plugin command` asks for explicit `yes` or `no` per stage.

The pure document-preparation query borrows allocation custody from the actual installed package descriptor. Before encoding or copying its independent frozen graph, the host pays the concurrent graph, codec and carrier allocations in that same original metadata bank. The query does not consume another independent 16 MiB reservation merely because an earlier continuation still owns its completed document observation. Original aggregate ceilings, message limits, node factors and native request/response reservations remain unchanged. This allocation loan is data only: it replaces no canonical document Source, read, CAS, capability, package-generation check, cancellation check or 5-second policy-call limit. The public Command regression in `support_tests/plugin_command_control_blackbox/check.py` keeps Todo revision 2 and Goal `set`, `budget 200`, then explicit `pause` in one running RPC application; its assertions inspect the actual canonical allowance and reject Model attempts, legacy state writes and unsettled operations.

A pure message is exactly `{ "schema": "axyndra.command-message/v1", "text": "..." }`, with nonempty UTF-8 text bounded to 16 KiB. It creates no Run, ToolCall, capability or user-control owner. Legacy bounded `content` messages remain supported.

Only a Command manifest contribution declaring `allowed_user_controls: ["continuation"]` can propose a continuation control. This declaration is not a capability grant. A Tool/Provider result, a public Product command call without the actual Application scope, a copied JSON object or restored history cannot create the host user-control scope. An explicit early control is visible from its first review. A deferred Command instead retains its original input and manifest declaration while the first review authorizes only the canonical document read. Its pure document preparation may then return `user_control` beside `intents`. Only the actual private Command participant accepts this field; an ordinary Tool or Provider cannot supply it. The host freezes the final control, complete parent arguments and canonical fact links once. The mutation review displays that final control and its new proposal digest; re-preparation may only confirm the same bytes. No control is selected when the field is absent. These previews are display data; the retained canonical operation and argument hash remain the execution authority.

The generic continuation control has `kind: "continuation"`, `document_key` and `action`. Create/replace/resume require `next_prompt`; create/replace/set_budget require `token_budget` (positive integer or null); pause/close accept neither. An actual host-held participant attaches only to the original Direct context. A selected control requires exactly one same-key document CAS, even if its document value is unchanged. A completed document CAS, its child Receipt, host accounting update and exact document version pin commit in the same SQLite transaction. The participant also compares the stored parent plan arguments to its private read-backed frozen arguments inside that transaction. A failure rolls them back together. The Application creates a live future-start owner only after the actual parent has completed. A budget-only control cannot reconstruct a missing live prompt; an explicit user resume is required. An early explicit control rejects this before creating a Run. A deferred raw command needs its real read first and rejects before any parent mutation or allowance update.

Each next Run uses the ordinary Core start machinery with a typed continuation SystemNote, the frozen model request and one consumed claim in the same transaction as Thread revision/Run/Turn admission. It creates no fake UserMessage, Tool invocation or extra model Attempt. The source and accounting are host facts, not plugin document fields. Existing Run statistics implement the old between-Run token gate; this is not a hard token limit inside an individual Run. Pause/revocation prevents the next admission and does not cancel an already admitted Run. Application cancel retains its usual cancellation behavior. New Application instances and DB reopening never reconstruct the live continuation owner from accounting/history.

This candidate remains dependent on the complete document broker, schema 28 foundation, continuation Core/Facts, Direct preparation-read, choice-preflight and installed Workflow package candidates. No portion is an independently enabled production bypass. Old Goal/Todo writers are not retired here.

Unverified and remaining compatibility work: all authored Cangjie and App black-box cases require builder execution; active-Run user pause/replace still needs an actual serialized control path because same-thread Direct admission rejects a busy Run; Goal `set` absent/active/paused selection is implemented by the required pure package companion and still needs actual combined validation; ordinary model document changes currently invalidate the exact pin conservatively, including progress-only edits; import/export/editor UI parity and old-writer retirement are separate prerequisites. Unlimited user budgets retain the old unbounded between-Run behavior and must be explicitly paused/cancelled by their user.
